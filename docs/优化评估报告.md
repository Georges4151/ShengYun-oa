## 二、方向一：性能与缓存

### 2.1 业务缓存完全缺失（P0）

全仓库没有 `@Cacheable`、`@CacheEvict`，也没有 `RedisTemplate` 业务缓存封装。Redis 目前只承担签名 nonce、文档编辑锁、分片上传、下载令牌、企业微信 token 与分布式锁，见 [RedisNonceStore.java](file:///e:/sxassist/src/main/java/com/ceams/common/sign/RedisNonceStore.java) 与 [DocLockServiceImpl.java](file:///e:/sxassist/src/main/java/com/ceams/module/doc/service/impl/DocLockServiceImpl.java)。

影响面：权限树与菜单在每个请求中重复查库；主数据字典（分类、材料、往来单位、设备）被高频读取；仪表盘与报表统计实时聚合。并发上来后，第一个打满的是 20 个 Hikari 连接。

改造点：按 Cache Aside 引入统一缓存组件，key 采用 `ceams:cache:{域}:{对象}:{id}:{维度}`，TTL 必须带随机抖动，删除缓存挂在事务 `afterCommit`。首批试点建议锁定「权限树 / 主数据字典 / 仪表盘统计」三个读多写少的接口，不碰金额与审批状态。

### 2.2 Redis 连接池会成为新瓶颈（P1）

[application.yml](file:///e:/sxassist/src/main/resources/application.yml#L24-L35) 中 `max-active: 8` 对纯锁场景够用，一旦承接业务缓存读，按现有接口并发会被连接池限流。加缓存前先调到 32～64，并保留「Redis 不可用降级直查库」的开关，避免缓存变成新的单点。

### 2.3 报表与统计的内存聚合（P1）

报表接口在 Java 层解密金额后汇总，属于合理的合规设计，但每次请求全量拉取再聚合，数据量增长后耗时线性上升。适合做 1～5 分钟短 TTL 缓存，key 必须包含「角色 + 日期区间 + 项目」，否则会把 A 的可见范围缓存给 B。强一致要求高的余额、审批状态继续直查。

### 2.4 列表关联字段回填（P2）

分包合同、结算凭证、设备租赁已按「收集 ID → 批量查询 → 回填」实现，但同类模式下仍有逐行组装的分页实现。建议在评估阶段逐页核对，优先处理数据量大的报表与待办列表。

## 三、方向二：后端结构与代码质量

### 3.1 巨型 Service（P1）

按文件体积排序：`HrPayrollServiceImpl`（47KB）、`HrPerformanceServiceImpl`（40KB）、`AiChatServiceImpl`（33KB）、`BpmTaskServiceImpl`（30KB）、`OnlyOfficeServiceImpl`（29KB）、`BpmFlowEngine`（29KB）、`AiDailySummaryServiceImpl`（28KB）、`ReconciliationServiceImpl`（25KB）。

这些类的共性是「计算 + 校验 + 持久化 + 通知」混在一个文件里，单测只能整体覆盖。改造方式是按职责拆为「规则计算器 / 查询服务 / 持久化编排」，先拆薪酬与绩效（两者规则变化最频繁），再拆 BPM 引擎。

### 3.2 持久层混用（P2）

89 个 Mapper 继承 `BaseMapper`，说明 MyBatis-Plus 已是事实标准；仅剩 2 处 `@Select` 与 3 个 XML，属于历史残留。建议统一到 MyBatis-Plus 的 `LambdaQueryWrapper`，把复杂查询收敛到 Mapper 接口的默认方法，避免 SQL 散落在 Service 中。

### 3.3 参数校验与异常语义（P2）

当前 DTO 上的校验注解与 Service 内的业务判断并存，错误码依赖 `BusinessException.of(ErrorCode...)`。建议统一「注解负责格式、Service 负责业务」的边界，并对高频错误码补中文文案映射（前端已有 `AUTH_TOKEN_INVALID` 的中文映射，可作为统一入口）。

## 四、方向三：前端工程化

### 4.1 巨型组件（P1）

前八大文件：`BpmView.vue`（35KB）、`AiAssistant.vue`（31KB）、`FlowDesigner.vue`（28KB）、`PerformancePanel.vue`（27KB）、`SubcontractorContractList.vue`（27KB）、`VehiclePanel.vue`（26KB）、`RepairPanel.vue`（24KB）、`ReceiptList.vue`（23KB）。

路由懒加载已具备，问题在页面内部「列表 + 弹窗 + 表单 + 详情」全部内联。建议按「列表面板 / 编辑弹窗 / 详情抽屉」拆分，BPM 视图优先，因为它同时包含模板、实例、任务三类交互。

### 4.2 打包体积（P1）

`chunkSizeWarningLimit` 被放宽到 1500，意味着默认配置下已经报警。全局引入了 `element-plus/dist/index.css`（见 `apps/web/src/main.ts`），组件虽按需 import，样式仍是整包。建议样式按需引入，并在 Vite 中增加 `manualChunks`，把 `element-plus`、`vue` 运行时、编辑器类依赖拆成独立 vendor chunk，首屏只加载当前路由需要的部分。

### 4.3 三端一致性（P2）

小程序构建只读 `.env.production` 与 `.env`，漏配 `VITE_API_BASE_URL` 会静默回退到占位域名，这是已发生过的线上问题。建议在三端构建脚本前加环境变量校验，缺失直接 fail，而不是运行时才暴露。错误码文案也建议收敛到 `packages/types`，三端共用一份映射。

## 五、方向四：质量保障与安全

### 5.1 高危链路缺幂等约束（P0）

[StampApprovalServiceImpl.java](file:///e:/sxassist/src/main/java/com/ceams/module/seal/service/impl/StampApprovalServiceImpl.java#L66-L90) 的 `create` 只校验申请为 PENDING 与印章为 ACTIVE，未校验「该申请是否已有审批单」，并发或重复点击会生成多条 PENDING 审批。建议增加「同一 stampId 仅一条 PENDING」校验，并在数据库层加唯一索引（新增 Flyway 迁移，不改历史脚本）。

### 5.2 测试分布不均（P1）

93 个测试类中，高危链路（用印签名、PDF 盖章、银行对账匹配、报销审批流转）缺少端到端集成测试。这四组恰好是「出错要赔钱或担责」的模块，建议优先补集成测试，覆盖签名时间窗、nonce 重放、状态机非法流转、并发审批四类场景。

### 5.3 可观测性不足（P1）

[application.yml](file:///e:/sxassist/src/main/resources/application.yml#L233-L240) 只暴露 `health,info`，没有 Micrometer 指标。建议引入 `micrometer-registry-prometheus`，至少埋三类指标：接口 p95 耗时、缓存命中率、业务失败计数（盖章失败、AI 超时、对账异常）。没有指标时，缓存与性能优化都无法验收。

### 5.4 安全遗留项（P2）

印章模块的 `passwordProtected` 字段目前只存在于实体与 VO，缺实际校验入口；使用审计的 `ipAddress` 需要确认所有写入路径已赋值；授权使用能力尚未实现。上述三项建议在下一轮安全整改中一并复核，避免只做展示字段。

依赖层面 Tika 已升至 3.2.3 并覆盖 `commons-lang3` 至 3.17.0，属于已知问题的正确处置；建议补充 OWASP dependency-check 到构建流程，并统一日志脱敏（手机号、身份证、金额）。

## 六、优先级与实施路线

| 优先级 | 事项 | 预期收益 | 风险 |
|--------|------|----------|------|
| P0 | 三个热点接口缓存试点 + 命中率埋点 | 热点接口耗时与数据库压力明显下降 | 缓存维度错误导致越权，需按角色拼 key |
| P0 | 用印审批幂等修复 + 迁移脚本 | 消除重复审批单 | 需回归现有审批流程 |
| P1 | Redis/Hikari 连接池调优与降级开关 | 避免缓存引入后成为新瓶颈 | 配置变更需压测验证 |
| P1 | Prometheus 指标 + 关键业务计数 | 优化效果可度量 | 需要部署侧配合抓取 |
| P1 | 薪酬/绩效/BPM 服务拆分 | 可测试性与改动成本下降 | 拆分类改动大，需回归 |
| P1 | BPM 等巨型组件拆分 + 打包分包 | 首屏体积与维护成本下降 | UI 回归需要逐页验证 |
| P1 | 四组高危链路集成测试 | 关键资金/用印流程可信 | 测试数据准备成本 |
| P2 | 持久层统一、错误码三端收敛、依赖扫描、日志脱敏 | 长期可维护性与合规 | 影响面宽，适合分批推进 |

建议分三步推进。第一步做「缓存试点 + 幂等修复 + 指标埋点」，改动集中、风险可控，并且能拿到优化前后的数据。第二步做「服务拆分 + 前端拆分 + 高危测试」，属于结构性改造，需要较长回归周期。第三步做「构建优化、安全扫描、AI 评测集」，可以在前两步稳定后滚动进行。

## 七、验收度量

缓存命中率目标不低于 80%，试点接口 p95 耗时下降 50% 以上，数据库 QPS 相应下降；用印重复审批单数量为零；前端首屏 JS 体积下降 30% 以上，最大 chunk 不超过 500KB；四组高危链路集成测试全部通过；Prometheus 能查到接口、缓存、业务失败三类指标。

## 八、需要确认的决策点

第一，缓存试点选哪三个接口，是否就按「权限树 / 主数据字典 / 仪表盘统计」推进。

第二，是否引入 Prometheus + Grafana 一套监控，还是先用日志打点过渡。

第三，用印审批加唯一索引需要新增 Flyway 迁移（V48），是否允许在本次改造中提交 DDL。

第四，前端巨型组件拆分是否接受逐页视觉回归的成本，还是只拆 BPM 与 AI 助手两个最高频页面。
